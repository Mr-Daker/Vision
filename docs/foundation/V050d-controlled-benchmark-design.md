# V050d — Controlled analytical benchmark design

**Status:** design only. No benchmark rows, seed, split, labels, model, or
BigQuery resource were generated by this task.

## 1. Decision this benchmark must support

The present planted set is useful for pipeline checks but too small for a
credible performance claim: scenarios have 10–26 cases and hidden strata have
3–8. V050d creates a fresh, controlled benchmark of 1,600 independent cases —
200 for each scenario A–H — with a fixed 70/30 development/hidden split. It
tests whether the frozen rule-based analyses can distinguish policy situations
that deliberately overlap in their observable evidence.

A case is one synthetic district-sector with 24 monthly observations and zero
or more project records. It is not a single report and is not assigned to a
real district name. Census-derived covariate profiles may be resampled as
templates, but every case uses an opaque identifier and an explicit
`synthetic_benchmark` provenance marker.

## 2. Scenario semantics and generation strategy

All scenarios share the same generator and observable schema. A label first
selects a distribution over latent need, participation, project coverage,
delivery effectiveness and temporal shape; observable reports, indicators and
projects are then sampled with noise. No scenario has a constant multiplier or
unique category value.

| Scenario | Policy meaning                            | Generation strategy                                                                                                                                       |
| -------- | ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A        | genuine unmet need / new investment gap   | high but overlapping latent need; no current project in most, not all, cases; flat-high or mildly rising demand                                           |
| B        | need already covered by an active project | A-matched need and participation; usually active funding, with ambiguous sanction/status records in a minority                                            |
| C        | possible execution/outcome gap            | a completed project inside the observation window; post-completion demand often fails to fall, but noise and scope mismatch prevent a deterministic label |
| D        | emerging crisis                           | ordinary-to-moderate baseline followed by a late rise whose onset, slope and magnitude overlap chronic and seasonal cells                                 |
| E        | persistent chronic issue                  | sustained elevated need with persistence and often delayed/stalled investment; may show modest trends so it is not separable from D by one slope          |
| F        | popularity bias                           | large/high-participation cases with high raw volume but modest per-capita need; tails overlap A/E raw counts                                              |
| G        | silent need / under-reporting             | high deficit with low realised participation; some cases receive sparse reports and some controls are quiet for benign reasons                            |
| H        | healthy / low priority                    | generally adequate infrastructure and low need, with noisy report spikes, legacy projects and imperfect indicators in the tails                           |

Covariate templates are matched in blocks across scenario pairs before latent
effects are applied: A/B/C/E on baseline need and population, D/E on baseline
volume, F/A on raw volume, and G/H on observed low volume. Template reuse is
limited to one grouped family, and the entire family stays in one split.

## 3. Exact counts and split

- 1,600 cases total; exactly 200 A, B, C, D, E, F, G and H.
- 1,120 development cases; exactly 140 per scenario.
- 480 hidden cases; exactly 60 per scenario.
- 38,400 monthly rows: 1,600 × 24.
- Project rows are sampled, expected at 1,500–3,500; their count is frozen in
  the manifest after generation rather than forced to an artificial target.

The split unit is `profile_group_id`, not a monthly row. Cases derived from the
same covariate template or matched counterfactual family can never cross the
development/hidden boundary. Within each scenario, groups are ordered by
`SHA256(split_salt | case_id)` and assigned until the exact 140/60 target is
met. The allocator refuses a set of group sizes that cannot meet the target;
it does not split a group to make the arithmetic work.

Public development assets contain development features and labels. Hidden
features and hidden labels are both withheld until the one-shot evaluator runs;
publishing hidden features while hiding only labels would still allow
transductive tuning.

## 4. Observable feature schema

`cases.parquet`:

```text
case_id STRING                       opaque random identifier
profile_group_id STRING              opaque grouping key used only by split validation
sector STRING                        water|roads|education|health
population FLOAT64
population_density FLOAT64
urbanization_proxy FLOAT64
digital_participation_score FLOAT64  observable platform-participation estimate
infrastructure_data_origin STRING    derived|real_anchor_template
data_origin STRING                   always synthetic_benchmark
generator_version STRING
```

`monthly_observations.parquet`:

```text
case_id STRING, month_index INT32, year INT32, month INT32
citizen_report_count INT64, unique_citizen_count INT64
canonical_issue_count INT64, reports_per_10k FLOAT64
avg_severity FLOAT64, high_severity_report_count INT64
persistent_issue_count INT64, avg_persistence_days FLOAT64
infrastructure_score FLOAT64, infrastructure_deficit_score FLOAT64
sanctioned_investment FLOAT64, released_investment FLOAT64
spent_investment FLOAT64, active_project_count INT64
completed_project_count INT64, delayed_project_count INT64
last_project_completion_date DATE, months_since_last_completion FLOAT64
```

`projects.parquet` mirrors the analytical project fields required by the
execution analysis: opaque project ID, case ID, sector, amounts, four dates,
status, scope and synthetic provenance. It contains no scenario text.

`labels.parquet`, stored separately, contains only:

```text
case_id STRING, scenario_code STRING
ground_truth_unmet_need BOOL
ground_truth_investment_gap BOOL
ground_truth_execution_gap BOOL
ground_truth_emerging_hotspot BOOL
ground_truth_silent_need BOOL
expected_interpretation STRING
```

Forbidden from every feature asset: scenario IDs/codes/names, expected
interpretation, any `ground_truth*`, latent need, latent quality, propensity
multiplier, trend label, investment profile label, seed-derived ordinal,
scenario-specific ID prefix, and generator branch/debug fields.

## 5. Leakage controls and sealing protocol

Generation is not allowed from a dirty worktree. Before the first row exists,
the evaluator records:

1. a clean generator commit SHA;
2. generator package version and configuration SHA-256;
3. feature-schema SHA-256;
4. a new 256-bit CSPRNG seed that has not been used in current-data analysis;
5. split algorithm version and a separately generated split salt;
6. declared counts: 200 per class, 140/60 split per class and 24 months.

The seed and salt are written to a private evaluator manifest, never printed to
CI logs or passed on a command line. A public SHA-256 commitment is recorded
before generation. The seed is revealed only after the final benchmark report
is frozen, enabling reproduction without enabling development-time tailoring.

Generation is one-shot. The tool refuses to overwrite a completed benchmark.
After generation it writes row counts and SHA-256 for every artifact, then
seals the hidden feature and label files read-only in evaluator-controlled
storage. The development command has no path or credential for hidden assets.
The final evaluator accepts a frozen method artifact/commit, runs it once on
hidden features, joins labels only after predictions are written, and emits an
append-only score report plus checksums.

## 6. Anti-triviality and distribution-overlap gates

Generation fails rather than merely warning when any of these checks fails:

- identifiers, category values and missingness predict scenario above chance
  in a permutation test;
- a feature name or value matches forbidden leakage patterns;
- a case or profile group occurs in both splits;
- duplicate 24-month feature vectors occur across splits;
- any scenario has other than 200/140/60 total/development/hidden cases;
- any single numeric feature achieves one-vs-rest ROC AUC above 0.80 on the
  development set, or a one-level decision tree achieves macro F1 above 0.70;
- an untuned shallow baseline exceeds macro F1 0.90, which triggers review for
  accidental shortcuts rather than celebration;
- a numeric feature has zero variance within a scenario;
- scenario-pair support is disjoint for a declared matching dimension.

Overlap is reported, not reduced to one gate: pairwise Jensen–Shannon
divergence for binned numeric features, overlap coefficient, two-sample KS
statistics, standardised mean differences, quantile ranges and classwise
missingness. At least 80% of each scenario's cases must fall inside the pooled
1st–99th percentile envelope for every continuous observable. Declared matched
pairs must have overlap coefficient at least 0.25 on their matching dimensions.
These thresholds are generator QA criteria, not model-selection targets.

## 7. Evaluation metrics

Classification is reported per policy target and as macro/micro summaries:
confusion matrix, precision, recall, specificity, F1, balanced accuracy and
Matthews correlation coefficient, with Wilson intervals for proportions.
Scenario-code prediction additionally reports per-class and macro F1. No metric
is reported without its numerator and denominator.

Ranking is reported for each shortlist at K = 10, 25, 50 and 100: hits,
Precision@K, Recall@K with its mathematical ceiling, NDCG@K and average
precision. Bootstrap confidence intervals resample whole profile groups, not
monthly rows. Development metrics may guide changes; hidden metrics are
generated once after the method is frozen.

## 9. Size and runtime estimate

Expected local output is 10–30 MB compressed Parquet: 38,400 monthly rows,
1,600 cases and roughly 1,500–3,500 project rows. Generation and validation
should complete in under two minutes on the laptop class that generates one
million report rows in about 42 seconds; the benchmark does not need raw
report-level text/media. A BigQuery copy would remain far below 1 GB and its
full scans would stay within free-tier-scale usage, but no cloud copy is part
of this design task.

## 10. Stop rule

Implementation must stop before generation if the tree is dirty, the generator
commit is not frozen, private seed storage is unavailable, hidden assets would
be visible to the development identity, or any count/leakage/overlap gate lacks
an executable test. V050d design approval does not authorise data generation,
threshold tuning, BigQuery ML, Vertex AI, UI work or deployment.

# V050c — Analytics evaluation against planted scenarios

Generated by `npm run analytics:report`. Every figure below comes from running the five analysis SQL files against the generated dataset and scoring the results against scenario labels the analyses never received.

## Leakage statement

No ground-truth column reached the analytics. The five analysis files are executed through local.run_file, which raises PermissionError if a query names an evaluation table; labels are read only after every analysis has produced its output, and joined in Python. In BigQuery the same separation is enforced by dataset permissions: the analytics service account has no read grant on voice_eval.

## What each signal was scored against

Each analysis is scored against the scenarios it is designed to detect, not against the union of all unmet-need labels. Scenario G is _defined_ as need that produces almost no reports; marking the demand-driven analysis wrong for missing it would punish the design for working as intended. The ensemble row scores the combination, which is the claim that actually matters to a policymaker.

## How to read these numbers

**Precision is a lower bound, not an accuracy.** Only 162 of 2,508 district-sector cells carry a planted scenario. The other 2,346 are ordinary cells generated from real district characteristics with genuine variation, and some of them really do have high demand over a poor infrastructure indicator with no project. Those count as false positives here because they were not planted, even where flagging them was the right call. A perfect analysis would not score 100%.

**The thresholds were not chosen blind.** A sensitivity analysis over the demand and deficit thresholds was run against these labels before the values in `02_unmet_need.sql` were fixed. The primary justification is shortlist size — the top ventile of 2,508 cells is a list a ministry can work through, the top quartile is not — but a reader should treat these figures as optimistic relative to a genuinely held-out threshold choice.

**A wide interval is reported as unreportable rather than as a number.** Several signals have fewer than 25 planted examples, and a precision of '3 of 9' cannot distinguish a method that usually works from one that works half the time. This mirrors `MAX_INTERVAL_WIDTH_FOR_A_RATE` in `packages/domain/src/evaluation.ts`.

## Known weaknesses

Three signals are materially weaker than the rest, and tuning them further against these same labels would be fitting to the evaluation set rather than improving the method:

- **Execution / outcome gap** — only a handful of planted cells have enough reports on both sides of a completion date for a before/after comparison to mean anything. The method is sound; the sample is thin.
- **Silent need** — the expected-reporting baseline is a mean within a deficit band, which is crude. This is the clearest candidate for a learned expected-reporting model, and the comparison against this baseline is what would justify adding one.
- **Monitor existing project** — inherits the recall ceiling of the unmet-need step that feeds it, so it cannot exceed that step's coverage.
